# Claude Code Subagents

Follow the shared [delivery contract](../northstar/SKILL.md#delivery-contract): finish the highest-value existing workflow, use one approval owner, and stop optional work at diminishing returns. Load this companion only for its current task.


Use this skill from Codex when the user asks to have Claude Code do work, or when a separate Claude Code run can make useful independent progress. Codex remains the orchestrator and accepting owner; Claude Code is a delegated worker. This is the host-specific fifth skill in Northstar's package.

## Decide whether to delegate

- The generic default is to delegate only when a bounded Claude Code task can improve speed, independent review, or focused expertise enough to justify startup, coordination, integration, and model cost; it applies only when no owner/repository mandate requires the parent to orchestrate and review CLI implementation workers.
- Under that mandate, dispatch one bounded write-enabled CLI implementation worker for every actionable criterion, even when work is simple, sequential, tightly coupled, or limited to one file; this does not require parallel workers. Independently review the handoff.
- Use local LiteLLM at `http://127.0.0.1:4000/v1` as Claude Code's primary model-inference source by default, not only for supporting tools. Use the exact loopback host exposed by the gateway; don't assume `localhost` resolves to the same listener. Use model ID `default` as a gateway alias for the currently saved routing-desk target regardless of alias/force/off mode. This does not pin the worker to Luna or another fixed model; LiteLLM chooses the configured target. If no target is saved, the gateway applies its own configured initial-target fallback. Verify the configured CLI protocol with one bounded read-only smoke request. Claude Code may require a protocol different from LiteLLM's OpenAI-compatible API; establish that the local service supports the CLI's actual protocol before dispatch, and do not redirect credentials or change saved settings to force it. If Claude Code cannot use this local route, stop and report the exact gap; use another route only after explicit owner authorization.
- For a process-isolated Windows invocation, create a dedicated, access-controlled `CLAUDE_CONFIG_DIR` that is empty before first use; do not point it at the user's normal Claude profile. Set `ANTHROPIC_BASE_URL=http://127.0.0.1:4000`, `ANTHROPIC_MODEL=default`, and `ANTHROPIC_DEFAULT_OPUS_MODEL`, `ANTHROPIC_DEFAULT_SONNET_MODEL`, `ANTHROPIC_DEFAULT_HAIKU_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, and `ANTHROPIC_CUSTOM_MODEL_OPTION` to `default` only in the Claude child process, and set all six explicitly there so the child process overwrites inherited ambient values: the text smoke that inherited non-default overrides exited 1 with an `unrecognized_model` diagnostic, while the smoke that set all six to `default` in the child returned the unique marker with exit 0. Those six variables changed together in one process-only bundle, so the pair is not causal proof for any single variable. Claude Code sends two different credentials under two different headers: `ANTHROPIC_API_KEY` is sent as the `X-Api-Key` header, and `ANTHROPIC_AUTH_TOKEN` is sent as `Authorization: Bearer <value>` ([official environment-variable reference](https://code.claude.com/docs/en/env-vars)). Populate `ANTHROPIC_API_KEY` only with an authorized LiteLLM inference virtual key for this exact local Subroute host; under `--bare` that variable is the authentication path the CLI reads. In that API-key/virtual-key mode, explicitly unset `ANTHROPIC_AUTH_TOKEN` in the Claude child environment rather than relying on it being absent: a prior failed invocation was traced to that variable overriding the expected `ANTHROPIC_API_KEY` route. `GATEWAY_MASTER_KEY` is a gateway-control credential, not an inference key, and must never be copied or mapped into `ANTHROPIC_API_KEY` in any mode; in API-key/virtual-key mode keep it in the orchestrator process only and remove it from the Claude child's environment. `ANTHROPIC_AUTH_TOKEN` is a distinct Bearer path, not a second name for `ANTHROPIC_API_KEY`: treat it only as an owner-authorized, process-only candidate for this exact local gateway, and accept it only after a successful Claude CLI unique-response smoke with that Bearer credential. Local Subroute documents that when `GATEWAY_MASTER_KEY` is set, API clients must send `Authorization: Bearer <GATEWAY_MASTER_KEY>`; such a gateway credential stays owner-authorized and process-scoped, is limited to this exact gateway, and is never mapped into `ANTHROPIC_API_KEY`. The Bearer path now has one passing Claude CLI text smoke against this exact local gateway: the child set all six model variables to `default`, kept the endpoint, model alias `default` and the same owner-authorized Bearer credential, and returned the unique marker with exit 0; that owner authorization covers the local route itself, so no separate credential request or key creation is needed for it. The earlier smoke that inherited non-default model overrides exited 1 with an `unrecognized_model` diagnostic naming model `MiniMax-M2.7[1m]` and query source `sdk`, and a debug-filtered rerun returned the same diagnostic with no request trace; that diagnostic's origin is still unproven, so it must not be attributed to auth, to the credential, or to any request, and no single override may be named as the cause. A passing text smoke still does not establish that Claude Code is usable for work. The first Bearer-backed Read/Edit task did exercise the allowed tools: it ran with `--tools Read Edit --allowedTools Read Edit --restricted --max-turns 5`, and its structured stream showed exactly two Read calls and six Edit calls, all inside its assignment, with no Bash or other tool call. It stopped at `error_max_turns` (`num_turns=6`, exit 1) before its final handoff, so it is capability evidence plus a failed handoff, not an accepted handoff. Its stderr also carried `[claude-code:unrecognized_model] {"model":"default[1m]","query_source":"sdk"}` with no correlated request sequence, which stays unclassified like the earlier diagnostic. Do not freeze future CLI work over this: do not repeat the same 5-turn invocation, and budget `--max-turns` to cover the Read/Edit work, the final verification, and the handoff. Do not mint credentials or change the endpoint, model alias, or provider to chase it. Apart from the single task-scoped creation allowed below, do not create, transform, or search for credentials. Keep the authorized key process-scoped; do not display or persist it, use it against any other host, or infer that it works for unrelated inference routes. Keep credentials out of command arguments, prompts, transcripts, logs, and files, and never write credentials or process-specific overrides to the user's global Claude settings. ([evidence](../../docs/reports/dispatch-context/claude-bearer-auth-20261023.md))
- When no suitable authorized inference key already exists for `http://127.0.0.1:4000` and the owner explicitly mandates delegating through Subroute, the orchestrator may create exactly one task-scoped LiteLLM virtual key through the local control API (`/key/generate`) and revoke it when the task ends. Scope it to model `default`, a unique task alias, `duration` and `budget_duration` of at most 20 minutes, `max_budget` of at most 0.5, and `max_parallel_requests` of 2. Evidence: a bounded Claude CLI Read/Edit task hit `ProxyRateLimitError` with limit 1 and remaining 0 before any native tool event, while an earlier Read-only smoke worked at 1; 2 is therefore the smallest tested candidate for CLI work, not a universal concurrency minimum or proof of reliability. The control call authenticates with the gateway master credential held in the parent only; never copy it into the child's environment. Read the generated secret only from the response field `key`, require a nonempty value carrying the `sk-` prefix, and never fall back to the `token` field, which carries a token hash instead of the plaintext key. Pass the virtual key only as the process-scoped `ANTHROPIC_API_KEY` of the Claude child. Revoke only the aliases this task created, in a `finally` path, through the API's `key_aliases` field rather than `keys`, then confirm the exact alias is absent via `key/list`; leave preexisting owner credentials untouched. If revocation fails, report the alias and its expiry and never the key. ([observed flow](../../docs/reports/dispatch-context/cli-trials.md#2026-10-22-subroute-claude-auth-and-tool-roundtrip-checkpoint))
- Check that `claude` is available and inspect its local version/help when the invocation depends on specific CLI options. Do not read or print credentials, tokens, or full provider settings. When supported, `claude auth status --json` can identify the selected auth method and credential source; inspect only those fields, never account identifiers or secrets.
- For local/custom routing, determine the effective base URL, model and auth source from safe environment values and the selected Claude profile's settings without displaying credentials. A process-level environment, user environment, and the active profile's `settings.json` can disagree; in most sessions, values under the settings file's `env` key override inherited shell values. Check which values the CLI will actually use. With a dedicated `CLAUDE_CONFIG_DIR`, inspect only that isolated profile and the child process environment; do not fall back to or expose the user's normal profile. If the effective credential's source/intent does not match the configured host, stop before making a request; do not send a key from one route to another host. Test the configured host, not an assumed port. For local Subroute, use an authorized LiteLLM inference virtual key; apart from the single mandated task-scoped creation above, do not create, transform, or search for credentials. Never substitute `GATEWAY_MASTER_KEY` for an inference key, and never display, persist, rewrite, or use the key against another host. A bounded CLI smoke must verify the exact key-host pairing. If the smoke returns 401 or otherwise rejects that credential, stop and inspect redacted gateway diagnostics together with that key's own metadata to identify the effective authentication source actually used; do not read unrelated token stores, change providers, models, endpoints, or credential sources, or launch tool-using work. Do not retry blindly: allow at most one corrected retry after a concrete authentication-source mismatch has been identified and corrected, otherwise stop and report the exact failure. Keep model alias `default` and the endpoint fixed at local Subroute (`http://127.0.0.1:4000`). An earlier task-keyed Claude CLI request to `POST /v1/messages?beta=true` returned `404 Not Found`; retain this as a historical CLI observation, not proof the route is currently broken or evidence of a bad key/backend cause. In a newer parent-authenticated synthetic HTTP request, `POST http://127.0.0.1:4000/v1/messages?beta=true` with model alias `default` returned HTTP 200 and the requested unique response. That request used the parent-only `GATEWAY_MASTER_KEY`, so it proves only that the endpoint/path and alias worked for that parent-authenticated HTTP request; it does not prove that a task-scoped virtual key works, that Claude Code works, or that Claude's native Read/tool-result roundtrip passes. The CLI virtual-key and native tool-result gates remain open. Do not map the master key into Claude or claim direct HTTP success as a Claude CLI pass. If another CLI 404 occurs, record its redacted URL, status/body and key metadata, then stop without changing model, provider or endpoint. See the official [environment-variable precedence](https://code.claude.com/docs/en/env-vars#precedence) guidance.
- If alias `default` is unavailable, inspect that same host's model catalog (usually `GET <base-url>/v1/models`) only to diagnose the failure. An advertised ID does not authorize changing the requested alias: keep `default`, run at most one bounded read-only smoke request against the same host, and stop if it fails. Do not try another model or route.
- Count the smoke test as usable only when the process exits successfully and returns the unique requested response. Keep stdout and stderr separate when possible: a gateway diagnostic on stderr does not erase a successful response, but record it and investigate if the response is missing or the exit status is nonzero. Do not infer success from `claude --version`, an open port, or a model catalog alone. A healthy Responses route, a passing Codex CLI smoke, or an advertised model does not substitute for Claude CLI's own unique-response smoke and its restricted tool-call/tool-result roundtrip.
- If the unique-response smoke succeeds with `default`, pass `--model default` to the bounded worker invocation. If it fails, stop that route and report the exact failure; do not change the model, endpoint, or credential source to continue the task.
- When the Claude client or the local route is new or has just been reconfigured, the orchestrator runs exactly one bounded smoke request in the Claude CLI itself, with `--bare`, a fresh empty isolated `CLAUDE_CONFIG_DIR`, `--model default`, and the fixed local Subroute endpoint, and passes that evidence (route, model ID, exit status, observed response) into the assignment. Reuse that evidence for subsequent tasks while the effective route configuration is unchanged; do not repeat route setup, launch nested CLIs, or troubleshoot the caller's wrapper from inside the child. The child works with the tools available in its own Claude session and reports an exact missing tool rather than improvising around it. A successful smoke establishes route usability only, not worker tool access, task completion or broad reliability.

## Give Claude Code a bounded assignment

Before launching it, define the result, observable acceptance, repository/base state, relevant instructions, owned write scope, verification, allowed side effects, and handoff format. Include known facts, unresolved assumptions, existing recovery history, and the next action. Carry the user's existing authority into the assignment; delegation cannot expand it.

For a tool-using task on local Subroute, verify the task's required route before starting Claude: send a bounded unique-marker request to `http://127.0.0.1:4000/v1/messages` with model alias `default` and the already-authorized, process-only Claude credential; then force a harmless `tool_use`, return its `tool_result` in a continuation, and confirm the marker. Keep the API's Anthropic `tool_use`/`tool_result` blocks intact. If the gateway reports a pre-inference failure (for example `supplemental_advisor_failed` and says the base request was not sent), do not launch Claude, retry the same request, or substitute credentials/routes; record the exact failure and use only an already-authorized fallback or independent work. A missing authorized inference key is a credential dependency: never use `GATEWAY_MASTER_KEY` or `EXPERTS_API_KEY` as a substitute.

Use Claude Code as one worker for one coherent scope. Do not let Codex and Claude Code write the same files at the same time. For shared-checkout work, pause Codex edits until Claude finishes. For parallel work, give each writer a distinct checkout based on the exact state it needs; verify the checkout's base before dispatch, since a CLI worktree option may start from a default branch rather than the current working state. Preserve uncommitted user changes.

For read-only review or investigation, prefer a noninteractive, read-only invocation when the local CLI supports it, for example:

```powershell
claude -p --permission-mode plan --max-turns 8 "Review <scope> against <criteria>. Do not edit files. Return evidence, findings, and remaining uncertainty."
```

For implementation or tasks requiring permission prompts, start Claude Code in the intended working directory with a clear task brief and use the configured permission flow. Never use `--dangerously-skip-permissions` to make delegation convenient. `--max-turns` limits agentic turns, not time spent waiting for API calls or retries. Put a wall-clock bound around each invocation and, when using Claude Code's `API_TIMEOUT_MS` or `CLAUDE_CODE_MAX_RETRIES` controls, set temporary process-level limits rather than changing saved settings. Capture stdout and stderr separately. For noninteractive `claude -p` runs, prefer `--output-format json` when the installed CLI supports it and record only the usage, timing, and cost metadata the run actually returns; leave missing metrics unknown, never infer usage from response length or model name, and keep stderr separate from parsed stdout. A noninteractive flag does not enforce a task deadline or limit all work. See the official [environment-variable reference](https://code.claude.com/docs/en/env-vars). When using local Subroute, pass the already-authorized inference virtual key only as process-scoped `ANTHROPIC_API_KEY`, which Claude Code sends as the `X-Api-Key` header; never use `GATEWAY_MASTER_KEY` as that key, and never map a gateway master credential into `ANTHROPIC_API_KEY` under any mode. `ANTHROPIC_AUTH_TOKEN` is a separate credential sent as `Authorization: Bearer <value>`; treat it only as an owner-authorized, process-only candidate for this exact local gateway, and accept it only after a Claude CLI unique-response smoke succeeds with that Bearer credential. One such text smoke now passes with the child process's model overrides set to `default`; the earlier smoke that inherited non-default overrides failed with an `unrecognized_model` diagnostic whose origin is unproven, and the single combined difference between the two runs is not causal proof for any one variable. Text-level success does not establish tool use: accept a Bearer-backed worker only after the parent has reviewed that worker's native Read/Edit tool events.

For a noninteractive implementation task, explicitly select the native tools the worker needs, for example Read, Edit, and a Bash command scoped to the test run, instead of relying on an implicit tool set. In one bounded trial, an invocation without explicit tool selection completed without changing the fixture, while the same task with explicitly selected Read/Edit and `Bash(node --test*)` tools edited the file and produced a parent-verified passing test run ([trial record](../../docs/reports/dispatch-context/cli-trials.md#2026-10-22-paired-implementation-trial-claude-repair-succeeds-codex-stopped)). That is one observed pair, not proof that explicit selection is required in general. Budget `--max-turns` so it covers inspect, edit, test, an optional repair, and the final handoff, and enforce the separate wall-clock deadline independently of the turn budget. A max-turn exit is an incomplete worker handoff even when the parent later verifies that the produced artifact passes, so record it as a failed handoff with an independently verified artifact. Choose the output mode by the evidence the run must produce: use `--output-format stream-json` and capture stdout incrementally into a task-scoped JSONL receipt when native tool lifecycle and handoff events must be shown, keep stderr separate from that stream, and on interruption preserve the partial receipt and mark it incomplete; use `--output-format json` when only the final response and usage metadata are needed.

### Observed bounded Read/Edit recipe

For a task-keyed implementation run through local Subroute, use the direct loopback API `http://127.0.0.1:4000/v1` and model alias `default`; launch Claude with `--bare` and a fresh isolated `CLAUDE_CONFIG_DIR`. Put the authorized task-scoped inference key only in the child process's `ANTHROPIC_API_KEY`; do not pass `GATEWAY_MASTER_KEY` or `EXPERTS_API_KEY` into the child. Bound the key to `max_parallel_requests=2`, `duration` and `budget_duration` no greater than 20 minutes, and `max_budget` no greater than 0.5. Explicitly allow only the native `Read` and `Edit` tools for this narrow recipe. Accept completion only when the structured event stream shows Read, Edit, and final Read, the worker supplies a handoff, the process exits 0, and the parent reviews the resulting diff against the assignment. Revoke exactly the temporary key alias in a `finally` path and verify it is absent afterward. One successful run took 11.76 seconds; this is a single observed trial, not a timing guarantee, reliability claim, or universal minimum. Preserve preceding failures and their context ([checkpoint and evidence](../../docs/reports/dispatch-context/cli-trials.md#2026-10-23-checkpoint-claude-task-key-concurrency-corrected-bounded-skill-edit-accepted)).

Claude Code may use its own native subagents for internal parallel work, but Codex still assigns one outcome and write boundary to the Claude Code run. Do not add another management layer unless Claude Code's task genuinely needs one.

## Integrate the handoff

1. Inspect the checkout and current diff before launch so user edits and the delegated base are clear.
2. On return, inspect changed files, command output, and actual checks. A Claude summary is a handoff, not proof.
3. Resolve gaps or conflicts within the mandate, preserving failed attempts. Do not ask Claude Code to retry an unchanged failed approach or treat reassignment as a recovery reset.
4. Integrate the smallest useful result and independently verify material acceptance criteria. If Claude Code authored or repaired the work, it cannot independently accept that same work.
5. Record the artifact, revision/base, checks actually run, observed result, gaps, and next action in the project's existing records. Count Codex setup, Claude usage, review, and rework as total effort; one successful task does not prove savings.

Use `claude -p` output or the interactive session transcript as evidence only for what it shows. Check `git status` after work and keep commits, pushes, publication, deployment, and external contact inside the user's actual authorization.
