# Technical debt

## A2A root scopes containing live operational state

Status: partially closed; priority: P2. Observed during the 2026-11-03 Instacart readiness work.

The default Northstar workspace contains its own `tmp/a2a-stack` state tree. A whole-workspace `.` scope therefore includes changing journals and live lock files; snapshotting can fail with `PermissionError`, and operational changes invalidate candidates. The corrected root matcher deliberately includes all authorized files and fails closed. It does not silently omit state or `.git`.

The current eight-file framework Goal and prepared nine-file Instacart Goal use explicit paths and avoid this overlap. Their acceptance does not establish stable self-hosted whole-root execution.

Closed on 2026-11-04: `GoalManager.create` now rejects a write scope that overlaps the operational state root, in both containment directions, before any baseline read and before any Goal is persisted. The refusal is a clear diagnostic, not a silent trim, so scope completeness is preserved. Verified by independent nonauthor review (READY) plus a supervisor live-service check over the real HTTP surface: an overlapping scope returns HTTP 400 with the diagnostic while a state file is held under a real exclusive Windows lock, and no goal directory or goal record is created; a safe scope still returns HTTP 201 with a baseline holding only the scoped source files.

Still open: there is no dedicated state-root setting. `SHARED_STATE_ROOT` is a hard-coded constant, so the only way to move the state tree outside the workspace is to select a workspace whose namespace already lives outside it. The diagnostic says so explicitly rather than promising a configuration that does not exist. An explicitly configured external state location, with a reviewed migration that preserves existing default-workspace data, remains the separate follow-up. Preserve completeness: do not quietly skip unreadable or changing scoped files. Verify with isolated lock/state fixtures before broadening the supported configuration.

## Windows checkpoint replacement contention

Status: open efficiency follow-up; priority: P2 while automatic recovery converges. On 2026-11-03 the actual Instacart Goal `g-2ab099f9f9424d93917be136905cf3da` recorded one `WinError 5` replacing `state.json`. The existing harness resumed the same session without interrupting its separate coding worker. The actual holder and cause remain unknown; this is not evidence of an external blocker.

Owned Windows 10.0.26200 / NTFS fixtures reproduced the error with a held ordinary reader. A reader allowing read/write/delete sharing still blocked `os.replace` of its open target, although renaming that open source to a new name succeeded. The proposed reader-only repair failed its effectiveness test and was reverted in the private copies; production was unchanged.

`ReplaceFileW` passed a limited open-target fixture with share-delete readers, but Microsoft documents partial-failure states (1176/1177) that can move or remove the destination. It was not adopted as an atomic writer. See [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) and [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew). The controlled fixtures establish a platform vulnerability, not attribution of the actual incident or crash/power-loss durability.

Reopen if contention repeatedly prevents progress or measured owner restarts warrant a dedicated fix. Preserve same-Goal recovery and atomic snapshots; do not silently weaken durability, overwrite in place, change file permissions, kill readers, or block the host event loop with an unbounded synchronous retry. A replacement must pass failure-state and concurrent-snapshot checks before deployment. Diagnostic evidence is retained privately under `tmp/a2a-stack/instacart-soak/state-reader-repair/`.

The later reviewed snapshot-recovery increment keeps the existing writer unchanged and avoids model diagnosis for recognized owned-state write errors only after recovery persistence succeeds. It also closes the post-spawn cleanup gap. These are separate from the unresolved Windows replacement API/holder investigation; neither establishes a new writer or attributes the original lock.

### Checkpoint writer reported the wrong failure

Closed on 2026-11-04: a separate defect in the same writer, confirmed by reproduction against unmodified production. The temp file was written outside the `try`, and `finally: temp.unlink` could raise and replace the in-flight error. The consequence was not cosmetic: `autonomy/runner.py::Journal.record` classifies a `PermissionError` by `winerror`, mapping `(5, 32, 33)` to `OwnedSnapshotUnavailable`, and `autonomy/manager.py` then retries that write with no ceiling. A replace failure carrying `winerror=87` (not recoverable) whose cleanup also failed with `winerror=5` was therefore reported as `5`, converting a permanent fault into an unbounded retry loop.

The repair moves the temp write inside the `try` and makes cleanup never replace an in-flight exception: the pending exception is captured before cleanup, and a cleanup `OSError` is attached to it as a note rather than substituted for it. On the success path a failing cleanup is still raised, because there is nothing to preserve. `a2a-stack/runtime/test_atomic_json.py` adds seven tests; five of them fail against the pre-fix writer, including the `87 != 5` misclassification. The sibling implementations in `agent/stacks.py`, `agent/task_store.py` and `autonomy/checks.py` were characterized separately: they already write inside the `try`, so they do not have the residue defect, but they do still mask a failing cleanup over the in-flight error. They were confirmed to have no unbounded-retry consequence, because none of their callers catches `PermissionError` or inspects `winerror`; only `runtime/runner.py` has a caller that classifies by `winerror` and then retries with no ceiling. Fixing them would expand the change without closing a demonstrated unbounded-retry path, so they are recorded as a separate follow-up rather than folded in. Evidence is in `D:/northstar-artifacts/a2a-stack/sibling-writers-characterization.json`.

Worker 3's contention regression (`test_checkpoint_contention.py`, seven tests) was run against unmodified production, where six pass and only the residue case fails; against the repaired writer all seven pass. That suite existed only in a private worker tree and was copied into this repository byte-for-byte so the regression is not lost with the worker; it is Windows-only by construction (`skipUnless(os.name == 'nt')`) and uses real file locks and child processes. Its `test_temp_write_failure_preserves_old_and_cleans_temp` is the residue case that fails against the pre-fix writer. Crash-temp cleanup after abrupt process death is still unmet, and the Windows replacement contention above is unchanged.

#### The atomic writer's second defect: a cleanup failure was swallowed and lost

Status: repaired, pending independent nonauthor acceptance; priority: P1. Found on 2026-11-04 by an independent nonauthor review of the atomic-write increment, which returned READY with six Suggestions and an explicit Unverified list. Two of the six were real defects in the repair itself and were confirmed by execution, not by reading.

The first is a swallowed cleanup failure. The repair captured the pending exception with `pending = sys.exc_info()[1]` inside the `finally`, and swallowed the cleanup error whenever `pending is not None`. `sys.exc_info()` reports the exception the current THREAD is handling, not the one the current frame is unwinding. When the writer has its OWN exception in flight the two agree, so the writer's own `winerror` was always the one reported. They diverge only when the writer has NOTHING in flight — the success path — where `sys.exc_info()` names whatever the thread is handling. Inside an outer `except` handler that is the OUTER error, so the writer concluded there was an in-flight failure to preserve and swallowed its own cleanup failure. The failure was lost with no diagnostic anywhere. Measured by probe (`D:/northstar-artifacts/a2a-stack/wa/probe_excinfo.py`) and by the reviewer's own `probe_matrix.py`: of the sixteen-cell cross product of writer outcome, outer-handler presence and cleanup outcome, the pre-fix tree reported the WRONG winerror in ZERO cells; the only cell that differs between the pre-fix and repaired trees is writer-succeeds / outer-handler-active / cleanup-fails, where the pre-fix tree swallowed the error and the repaired tree raises it. The repair captures the exception in the frame that is unwinding, via an explicit `except BaseException as exc: pending = exc; raise` nested inside the `try`, so `pending is None` exactly when there is nothing to preserve.

This correction matters for the record, because the earlier description of this defect overstated it. The winerror misclassification — a permanent fault reported as a recoverable sharing violation and retried with no ceiling — was real, but it belonged to the ORIGINAL writer at base commit `ac4358b`, whose `finally: temp.unlink` had no exception capture at all: there, a replace failure carrying `winerror=87` whose cleanup also failed with `winerror=5` was reported as `5`. Measured against that original writer: all four shapes report `winerror=5`. The `sys.exc_info()` repair had already fixed that; what remained was the swallowed success-path cleanup failure. The stakes are therefore a lost diagnostic, not an unbounded retry, and the code comments and test docstrings now say so. The autonomy reachability is real but is about the DIAGNOSTIC, not the classification: `autonomy/runner.py` calls `journal.record(...)` (and therefore `runtime.atomic_json`) from inside `except Exception as exc:` blocks at lines 738 and 789, and `autonomy/manager.py:446-460` retries a write classified `OwnedSnapshotUnavailable` with no ceiling, so a genuinely misreported `winerror` would still matter — which is why the honest-reporting property is preserved and tested even though the pre-fix tree already satisfied it.

The second is an unreachable skip guard. `runtime/test_checkpoint_contention.py` bound `K = ctypes.WinDLL('kernel32', use_last_error=True)` at MODULE level while the test class was guarded by `@unittest.skipUnless(os.name == 'nt', ...)`. On a non-Windows host the module-level binding raises at IMPORT time, so the skip guard is never reached and the module is an import error rather than a skip. Measured: with `ctypes.WinDLL` made unavailable, the pre-fix module fails to import with "kernel32 not available on this platform"; the kernel32 binding is now lazy behind a `_kernel()` accessor, so the module imports on any host and the guard is reachable.

Advisor Council consulted (gemini-3.8-flash-advisor, request_id chatcmpl-agy-d34d97bf74a0) on the repair design and approved it with one MANDATORY refinement, which was applied: when `BaseException.add_note` is unavailable the cleanup error must be attached as an attribute rather than re-raised, because re-raising it would reintroduce the masking this increment removes; and that attribute assignment must itself be wrapped in `try/except Exception: pass`, because some built-in exception types reject arbitrary attribute assignment and the assignment must not replace the in-flight error. The advisor's remaining suggestion — unbinding `exc` in the `finally` to avoid delaying frame GC — was measured and NOT applied, because it is actively harmful: Python already deletes the `except ... as exc` binding when the except block exits, so `del exc` in the `finally` raises `NameError: cannot access local variable 'exc'`, and a `NameError` raised inside the `finally` would replace the in-flight exception — the very masking this increment removes. Measured by probe (`D:/northstar-artifacts/a2a-stack/wa/probe_del_exc.py`).

A second independent review of this repair returned NOT READY with two must-fix findings, both confirmed by the supervisor by execution rather than by reading. The first (M1) is the corrected mechanism above: the repair's own stated defect narrative was wrong, and the new test's docstring asserted a mechanism the measurements contradict, so a future maintainer would believe the writer can misreport its winerror. The code comments and the test docstrings were rewritten to state the mechanism that actually exists. The second (M2) is that the new test file asserted on `__notes__` unconditionally, which is a 3.11+ mechanism, while the repair's own rationale cites 3.10 as an admitted interpreter — so the suite failed 2 of 11 on CPython 3.10.20 even though the repaired writer behaves correctly there. The assertions now accept either attachment mechanism, so the suite is green on 3.10 through 3.13. A third finding (S1) was that the attribute fallback introduced for 3.10 was DEAD CODE on every interpreter where the suite is green, because `hasattr(exc, "add_note")` is always True for any `BaseException` subclass on 3.11+; two new tests now force and check that branch directly. A fourth (S2) recorded a fourth independent atomic writer, `a2a-stack/scheduler/worker.py:29`, with its own `mkstemp`+`os.replace` and no `PermissionError` retry; it writes `STATE_DIR/<role>.json` in a separate container and separate volume, does not touch the goal state checkpoint, and is recorded as a suggestion rather than a demonstrated defect. A fifth (S3) corrected the reachability pointers: the calls are at `autonomy/runner.py:738` and `:789`, the winerror mapping is at `autonomy/runner.py:245`, and the unbounded retry loop is at `autonomy/manager.py:446-460`.

`a2a-stack/runtime/test_atomic_json.py` now holds thirteen tests. Two of them fail against the pre-fix writer and pass against the repaired one — `test_cleanup_failure_inside_an_outer_handler_is_not_swallowed` with "AssertionError: PermissionError not raised", and `test_attribute_fallback_attaches_the_cleanup_error_without_add_note` — so both are genuine regressions rather than descriptions of the new code. Three further Suggestions from the first review were applied as the reviewer's exact intent: the contention fixture now roots under `tmp/a2a-stack/checkpoint-fixtures` rather than the repo-root `tmp/checkpoint-fixtures` (the stack's own convention, and inside the `a2a-stack` namespace other tooling prunes); the contention module now sets `A2A_TEST_CONTROL_DIR` before `import runner`, exactly as `test_atomic_json.py` and `test_runner.py` already do, removing an import-order dependency on whichever module `unittest discover` loads first; and the unused `time` import was removed, a module docstring added, and the trailing blank lines normalized. No existing test, method or assertion was modified, deleted, skipped or loosened; the changes to the atomic_json test file are additive and the two renamed assertions accept either attachment mechanism rather than being weakened. Full-suite verification in the real tree with the real project venv: runtime 34 OK, agent 135 OK, autonomy 125 OK; `test_atomic_json.py` alone is green on CPython 3.10.20, 3.11.14, 3.12.11 and 3.13.11. At this point the increment was uncommitted pending independent nonauthor acceptance. Evidence is in `D:/northstar-artifacts/a2a-stack/atomic-write-qa-report.txt`, `D:/northstar-artifacts/a2a-stack/qa-atomic2-report.txt`, `D:/northstar-artifacts/a2a-stack/wa/` and `D:/northstar-artifacts/a2a-stack/prefix-excinfo/`.

## Claude shared auto-memory writes outside isolated source scope

Status: closed for the default Claude child paths; priority: P2. Closed native tool-path metadata for the formal-review/Claude-wait repair records three writes under the shared Claude project-memory directory, outside its private source write scope. Prior bytes were not captured, so no deletion or rollback was attempted. Candidate source correctness and the final isolated Python test audit do not establish native worker scope compliance.

Closed on 2026-11-04: both Claude child spawn sites now pin `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, child-only, in the copied environment and in the inline `--settings` payload, alongside the existing background-wait flag. `agent/service.py` `_child_env(True)` and `autonomy/runner.py` `NativeBackend.process` for the owner and supervisor channels set it; a non-Claude check child keeps exactly the inherited environment, and the parent environment is never mutated. The two strict full-map settings assertions were expanded to `{"env": {BG_WAIT_FLAG: "0", AUTO_MEMORY_FLAG: "1"}}`; every original test method and unrelated assertion is retained, and new cases are additive.

The flag was verified against the installed CLI rather than assumed. A control run without it wrote a native auto-memory file into a throwaway project memory directory; the same prompt with the flag produced zero memory files. The installed Claude Code 2.1.251 binary contains the `CLAUDE_CODE_DISABLE_AUTO_MEMORY` gate. The real Northstar project memory store was not touched by that test and the control's global-config side effect was reverted.

Both delivery mechanisms were then verified independently, because they are redundant by design and either could have been the inert one. The CLI honors only the **last** `--settings` occurrence, so a flag added as a separate occurrence would have silently discarded the other; both production sites therefore already use a single combined payload, which was confirmed by experiment and is recorded in `D:/northstar-artifacts/a2a-stack/claude-cli-settings-semantics.json`. A three-arm run against the installed CLI showed a control arm writing two native memory files, a plain-environment arm writing zero, and an arm where the flag was delivered ONLY through the inline `--settings` payload (with the child environment variable removed) also writing zero. So the `--settings` route is effective on its own and neither mechanism depends on the other; evidence is in `D:/northstar-artifacts/a2a-stack/auto-memory-settings-route.json`. The throwaway project namespaces from that run were removed afterwards and the real Northstar memory store was left untouched.

Scope limit: this suppresses native automatic memory reads and writes for those child paths. It is not an OS sandbox for arbitrary tool access, and it does not address any other writer to the shared memory directory.

Independent nonauthor acceptance on 2026-11-04: **READY**, bound to the four-file working-tree bytes. The reviewer found no defect in scope, confirmed both delivery routes are independently effective, confirmed the single-combined-`--settings` shape honors the last-occurrence-wins invariant, and confirmed the two strict payload assertions were expanded rather than loosened with no skip added or removed. The reviewer's own session had no execution capability, so the three green suites (runtime 28 OK, autonomy 106 OK, agent 104 OK) and a 14/14 external probe are the supervisor's evidence of record rather than the reviewer's own reproduction; the reviewer bound to the candidate by re-reading every scoped region and confirmed the content was byte-identical to the hashed bytes it was given.
