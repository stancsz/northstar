# Technical debt

## A2A root scopes containing live operational state

Status: partially closed; priority: P2. Observed during the 2026-11-03 Instacart readiness work.

The default Northstar workspace contains its own `tmp/a2a-stack` state tree. A whole-workspace `.` scope therefore includes changing journals and live lock files; snapshotting can fail with `PermissionError`, and operational changes invalidate candidates. The corrected root matcher deliberately includes all authorized files and fails closed. It does not silently omit state or `.git`.

The current eight-file framework Goal and prepared nine-file Instacart Goal use explicit paths and avoid this overlap. Their acceptance does not establish stable self-hosted whole-root execution.

Closed on 2026-11-04: `GoalManager.create` now rejects a write scope that overlaps the operational state root, in both containment directions, before any baseline read and before any Goal is persisted. The refusal is a clear diagnostic, not a silent trim, so scope completeness is preserved. Verified by independent nonauthor review (READY) plus a supervisor live-service check over the real HTTP surface: an overlapping scope returns HTTP 400 with the diagnostic while a state file is held under a real exclusive Windows lock, and no goal directory or goal record is created; a safe scope still returns HTTP 201 with a baseline holding only the scoped source files.

Still open: there is no dedicated state-root setting. `SHARED_STATE_ROOT` is a hard-coded constant, so the only way to move the state tree outside the workspace is to select a workspace whose namespace already lives outside it. The diagnostic says so explicitly rather than promising a configuration that does not exist. An explicitly configured external state location, with a reviewed migration that preserves existing default-workspace data, remains the separate follow-up. Preserve completeness: do not quietly skip unreadable or changing scoped files. Verify with isolated lock/state fixtures before broadening the supported configuration.

### Checkpoint writer reported the wrong failure

Closed on 2026-11-04: a separate defect in the same writer, confirmed by reproduction against unmodified production. The temp file was written outside the `try`, and `finally: temp.unlink` could raise and replace the in-flight error. The consequence was not cosmetic: `autonomy/runner.py::Journal.record` classifies a `PermissionError` by `winerror`, mapping `(5, 32, 33)` to `OwnedSnapshotUnavailable`, and `autonomy/manager.py` then retries that write with no ceiling. A replace failure carrying `winerror=87` (not recoverable) whose cleanup also failed with `winerror=5` was therefore reported as `5`, converting a permanent fault into an unbounded retry loop.

The repair moves the temp write inside the `try` and makes cleanup never replace an in-flight exception: the pending exception is captured before cleanup, and a cleanup `OSError` is attached to it as a note rather than substituted for it. On the success path a failing cleanup is still raised, because there is nothing to preserve. `a2a-stack/runtime/test_atomic_json.py` adds seven tests; five of them fail against the pre-fix writer, including the `87 != 5` misclassification. The sibling implementations in `agent/stacks.py`, `agent/task_store.py` and `autonomy/checks.py` were characterized separately: they already write inside the `try`, so they do not have the residue defect, but they do still mask a failing cleanup over the in-flight error. They were confirmed to have no unbounded-retry consequence, because none of their callers catches `PermissionError` or inspects `winerror`; only `runtime/runner.py` has a caller that classifies by `winerror` and then retries with no ceiling. Fixing them would expand the change without closing a demonstrated unbounded-retry path, so they are recorded as a separate follow-up rather than folded in. Evidence is in `D:/northstar-artifacts/a2a-stack/sibling-writers-characterization.json`.

Worker 3's contention regression (`test_checkpoint_contention.py`, seven tests) was run against unmodified production, where six pass and only the residue case fails; against the repaired writer all seven pass. #### The atomic writer's second defect: a cleanup failure was swallowed and lost

Status: repaired, pending independent nonauthor acceptance; priority: P1. Found on 2026-11-04 by an independent nonauthor review of the atomic-write increment, which returned READY with six Suggestions and an explicit Unverified list. Two of the six were real defects in the repair itself and were confirmed by execution, not by reading.

The first is a swallowed cleanup failure. The repair captured the pending exception with `pending = sys.exc_info()[1]` inside the `finally`, and swallowed the cleanup error whenever `pending is not None`. `sys.exc_info()` reports the exception the current THREAD is handling, not the one the current frame is unwinding. When the writer has its OWN exception in flight the two agree, so the writer's own `winerror` was always the one reported. They diverge only when the writer has NOTHING in flight — the success path — where `sys.exc_info()` names whatever the thread is handling. Inside an outer `except` handler that is the OUTER error, so the writer concluded there was an in-flight failure to preserve and swallowed its own cleanup failure. The failure was lost with no diagnostic anywhere. Measured by probe (`D:/northstar-artifacts/a2a-stack/wa/probe_excinfo.py`) and by the reviewer's own `probe_matrix.py`: of the sixteen-cell cross product of writer outcome, outer-handler presence and cleanup outcome, the pre-fix tree reported the WRONG winerror in ZERO cells; the only cell that differs between the pre-fix and repaired trees is writer-succeeds / outer-handler-active / cleanup-fails, where the pre-fix tree swallowed the error and the repaired tree raises it. The repair captures the exception in the frame that is unwinding, via an explicit `except BaseException as exc: pending = exc; raise` nested inside the `try`, so `pending is None` exactly when there is nothing to preserve.

This correction matters for the record, because the earlier description of this defect overstated it. The winerror misclassification — a permanent fault reported as a recoverable sharing violation and retried with no ceiling — was real, but it belonged to the ORIGINAL writer at base commit `ac4358b`, whose `finally: temp.unlink` had no exception capture at all: there, a replace failure carrying `winerror=87` whose cleanup also failed with `winerror=5` was reported as `5`. Measured against that original writer: all four shapes report `winerror=5`. The `sys.exc_info()` repair had already fixed that; what remained was the swallowed success-path cleanup failure. The stakes are therefore a lost diagnostic, not an unbounded retry, and the code comments and test docstrings now say so. The autonomy reachability is real but is about the DIAGNOSTIC, not the classification: `autonomy/runner.py` calls `journal.record(...)` (and therefore `runtime.atomic_json`) from inside `except Exception as exc:` blocks at lines 738 and 789, and `autonomy/manager.py:446-460` retries a write classified `OwnedSnapshotUnavailable` with no ceiling, so a genuinely misreported `winerror` would still matter — which is why the honest-reporting property is preserved and tested even though the pre-fix tree already satisfied it.

The second is an unreachable skip guard. `runtime/test_checkpoint_contention.py` bound `K = ctypes.WinDLL('kernel32', use_last_error=True)` at MODULE level while the test class was guarded by `@unittest.skipUnless(os.name == 'nt', ...)`. On a non-Windows host the module-level binding raises at IMPORT time, so the skip guard is never reached and the module is an import error rather than a skip. Measured: with `ctypes.WinDLL` made unavailable, the pre-fix module fails to import with "kernel32 not available on this platform"; the kernel32 binding is now lazy behind a `_kernel()` accessor, so the module imports on any host and the guard is reachable.

Advisor Council consulted (gemini-3.8-flash-advisor, request_id chatcmpl-agy-d34d97bf74a0) on the repair design and approved it with one MANDATORY refinement, which was applied: when `BaseException.add_note` is unavailable the cleanup error must be attached as an attribute rather than re-raised, because re-raising it would reintroduce the masking this increment removes; and that attribute assignment must itself be wrapped in `try/except Exception: pass`, because some built-in exception types reject arbitrary attribute assignment and the assignment must not replace the in-flight error. The advisor's remaining suggestion — unbinding `exc` in the `finally` to avoid delaying frame GC — was measured and NOT applied, because it is actively harmful: Python already deletes the `except ... as exc` binding when the except block exits, so `del exc` in the `finally` raises `NameError: cannot access local variable 'exc'`, and a `NameError` raised inside the `finally` would replace the in-flight exception — the very masking this increment removes. Measured by probe (`D:/northstar-artifacts/a2a-stack/wa/probe_del_exc.py`).

A second independent review of this repair returned NOT READY with two must-fix findings, both confirmed by the supervisor by execution rather than by reading. The first (M1) is the corrected mechanism above: the repair's own stated defect narrative was wrong, and the new test's docstring asserted a mechanism the measurements contradict, so a future maintainer would believe the writer can misreport its winerror. The code comments and the test docstrings were rewritten to state the mechanism that actually exists. The second (M2) is that the new test file asserted on `__notes__` unconditionally, which is a 3.11+ mechanism, while the repair's own rationale cites 3.10 as an admitted interpreter — so the suite failed 2 of 11 on CPython 3.10.20 even though the repaired writer behaves correctly there. ## A test lane wrote receipts into the Git working tree

Closed on 2026-11-04, found by the supervisor by reproduction while the atomic-write independent review was running. `a2a-stack/agent/test_coder_concurrency.py` executes `service.py`'s `RegisteredJobExecutor` from an AST-extracted namespace, and the receipt-contract increment changed the executor's terminal-receipt write from `runner.atomic_json(TASKS_DIR / task_id / "terminal.json", ...)` to a direct `path.hardlink_to(staging)` publish inside `RegisteredJobExecutor._write_terminal_receipt`. The new write no longer goes through `runner.atomic_json`, so the fixture's recording stub (`atomic_json=lambda path, value: receipts.append(value)`) no longer intercepted it, and the receipt landed on disk under the fixture's `TASKS_DIR`, which the namespace pinned to `HERE / "unused-no-write"` — inside the repository. Running the agent lane therefore created `a2a-stack/agent/unused-no-write/fixture-1/terminal.json` and `fixture-2/terminal.json`, and `git status --porcelain` listed `?? a2a-stack/agent/unused-no-write/`.

The consequence was not cosmetic. The repository is a shared working tree, and `git status --porcelain` is the mechanism that binds an independent review to a candidate tree: a reviewer compares the status at the start and the end of the review, and any stray file makes the acceptance void. A test lane that writes into the repository therefore destroys the evidence mechanism for any increment under review, and leaves untracked residue in the owner's tree. Every other agent-lane test roots its scratch under the stack's own ignored tree — `tmp/a2a-stack/receipt-contract`, `tmp/a2a-stack/receipt-withdrawal`, `tmp/a2a-stack/monitor-resilience`, `tmp/a2a-stack/goal-completion-tests` — and only the repository-root `/tmp/` is gitignored, so the scratch root must be `<repo>/tmp/a2a-stack/...` for the residue to be ignored as well as external.

The repair points the fixture's `TASKS_DIR`/`STATE_ROOT` at `<repo>/tmp/a2a-stack/coder-concurrency`, in a `tempfile.TemporaryDirectory` cleaned up in `tearDown`, and adds a regression guard that asserts the receipt is published inside the scratch root and that the lane adds no receipt anywhere in the repository tree. Building the guard surfaced two further defects in the fixture that had been masked: all three tests reused the task ids `fixture-1` and `fixture-2`, and because the executor publishes its receipt by an EXCLUSIVE link, a receipt that already exists makes the publish a no-op — so one test's receipt masked another's and the guard could not observe a publish at all. The task ids are now unique per test. The pre-existing residue was removed from the working tree.

The guard was falsified by reverting the repair in a scratch copy outside the repository: the lane then wrote eight stray receipts and the guard failed on the assertion that names the defect, "the lane wrote a receipt into the repository tree". Lane measurements in the real tree with the real project venv: runtime 34 OK, agent 136 OK (135 before the guard), autonomy 125 OK. Evidence is in `D:/northstar-artifacts/a2a-stack/coder-fixture-write/` and `D:/northstar-artifacts/a2a-stack/coder-fixture-falsify/`.

An independent nonauthor review of this increment returned READY with no must-fix findings and two Suggestions, both of which were real weaknesses in the guard rather than in the repair, and both of which are now closed. The first is that the guard's repository scan covered only `a2a-stack/agent` while its docstring and failure message claimed the whole repository tree. The reviewer proved the gap by pointing `TASKS_DIR` at the repository root — inside the repository but outside the agent directory — and showing the repository-write assertion passed while a receipt was really written into the tree; the test failed only on the later "no terminal receipt" assertion, which is a misleading message for a repository-write regression. The scan now walks the whole repository with `os.walk`, pruning `.git`, `tmp`, `__pycache__`, `node_modules` and `.wrangler`; the `tmp` tree is pruned because it legitimately holds about ninety receipts and scanning it would make the comparison meaningless. The pruned walk costs 0.18s and reports nothing on the real tree. The second is that the in-file comment justifying the unique task ids stated the mechanism imprecisely: the ids are not needed while the repair is in place, because each test then has its own scratch directory, but they ARE what makes the guard effective in the reverted state the guard exists to catch, where `TASKS_DIR` is shared and the executor's exclusive-link publish becomes a no-op against a receipt an earlier test left behind. The comment now says so. The reviewer also showed that a PER-TEST baseline for the repository scan is blind to a receipt written by an earlier test in the same class, so the baseline is now taken once in `setUpClass`, before any test in the class runs.

The guard was falsified in three separate variants after these repairs, each in a scratch copy outside the repository: the original revert to `HERE / "unused-no-write"`; a revert to the repository ROOT, outside `a2a-stack/agent`, which the pre-review guard could not see; and the original revert with the shared task ids restored, which made the pre-review guard's repository-write assertion blind. All three now fail on the assertion that names the stray receipts.

The re-review of those repairs returned READY with both suggestions CLOSED, and found two further residual weaknesses in the guard's coverage, neither a must-fix but both real. The first is that the prune set was broader than the set of directories git actually ignores: `.gitignore`'s `/tmp/` rule is ROOT-ANCHORED, so only the repository-root `tmp/` is ignored, while the prune matched `tmp` by BASENAME at any depth. The reviewer proved the gap by pointing `TASKS_DIR` at a nested `tmp/` and at `.wrangler/` — neither of which is gitignored, and `.wrangler/` is currently an untracked entry in `git status --porcelain` — and showing the repository-write assertion passed while eight receipts really sat on disk, with the test failing only on the misleading "the executor published no terminal receipt" message. The prune set is now `.git`, `__pycache__` and `node_modules` by name, plus the repository-root `tmp/` by ABSOLUTE path; a nested `tmp/` and `.wrangler/` are scanned. The second is that the baseline was a wall-clock tree snapshot, so a receipt written by an UNRELATED concurrent writer between the snapshot and the assertion was attributed to this lane and failed the test. That was not reachable in the current tree, but this repository is written to by several agents at once, so a spurious failure blaming this lane was reachable during a concurrent review.

Both are closed by the same change: the guard now identifies its own receipts by CONTENT rather than by position or by when they appeared. Each publish carries a lane-unique token in its task id, and the guard walks the whole repository and reports only the receipts whose task id carries that token. The tree snapshot, and the class-level baseline that replaced it, are gone, so an unrelated writer can no longer cause a false failure, and a receipt in a nested `tmp/` or `.wrangler/` is now found. The lane's task counter was also moved to a class-level attribute, because a per-test counter restarted at 1 in each test and so produced repeated task ids across the class — and a repeated id lets an earlier publish mask a later one, since the executor publishes by an exclusive link. With the counter shared, the guard detects the strays even when the counter is deliberately reverted to the masking shape.

The guard was falsified in five variants after these repairs, each in a scratch copy outside the repository: the original revert; a revert to the repository ROOT; a revert to a nested `tmp/`; a revert to `.wrangler/`; and a revert with the per-test counter restored. All five fail on the assertion that names the stray receipts. A separate probe confirmed that a receipt planted by an unrelated writer into a git-visible directory does NOT fail the lane.

The third review round returned READY with both of the round-2 suggestions CLOSED, and found one further Suggestion of the SAME family: `node_modules` was still pruned by name, but it is not in this repository's `.gitignore`, so a receipt in a `node_modules/` directory was invisible to the guard and the test failed on the misleading "the executor published no terminal receipt" message. The reviewer noted that pruning `__pycache__` by name is correct here, because that `.gitignore` rule has no leading slash and so matches at any depth.

Rather than patch the name list a fourth time — the list had already been shown to be broader than git's own ignore rules, twice, and each patch would have left the same class of gap for the next directory name — the prune set is now DERIVED FROM GIT. The guard runs `git ls-files --others --ignored --exclude-standard --directory -z` and prunes exactly the directories git reports as ignored, plus `.git`. On this repository that returns thirteen entries in 24ms: the repository-root `tmp/`, the `__pycache__/` trees, `.claude/`, `.pytest_cache/`, `.env`, `a2a-stack/scratchtmp/` and the `scheduled_tasks.lock`. `node_modules` is not among them, because git does not ignore it, so it is scanned. The set is read at the time the guard runs rather than hardcoded, so a directory that becomes visible later is no longer pruned. The scan cost on the real tree is unchanged: 318 directories, 992 files, 0.011s.

The guard was then falsified in five variants again, all failing on the assertion that names the stray receipts, and the `node_modules` variant — the one the reviewer had found blind — now fails there too. The unrelated-writer probe still passes.

The fourth review round ran out of turn budget (`error_max_turns`) before it could write its report, but its transcript records that C3, C4, C5 and C7 passed cleanly, that all three lanes passed (runtime 34, agent 136, autonomy 125), and that all five falsification variants failed on the correct assertion. It also raised the ignore-source anomaly that the supervisor then traced to its root cause, and it independently found the defect described next.

Two defects in the guard itself were confirmed by execution. The first is that `git_ignored_directories()` did not do what its docstring claimed: it returned an empty set only when git exited NON-ZERO, but when git was absent altogether `subprocess.run` raised `FileNotFoundError`, which propagated out of the guard and turned the lane into an ERROR rather than a pass. The empty-prune-set fallback is the safe direction — an empty set scans MORE of the tree and therefore cannot hide a receipt — but it was never reached, because the failure happened before the return code could be examined. The call is now wrapped so that an absent or unrunnable git yields an empty prune set, and the subprocess is bounded by a timeout so a wedged git cannot hang the lane. With git removed from `PATH` the lane now passes instead of erroring. The second is that the guard excluded its own scratch root only by git's opinion, so when git could not be consulted the lane reported its OWN receipts — the ones it had just published into its scratch directory — as strays. The scratch root is now excluded unconditionally by path, so the guard does not depend on git to know where its own receipts belong.

The ignore-source anomaly that the reviewer raised is resolved and is NOT a defect in the guard. `git check-ignore -v .claude/` reported a rule at `.gitignore:24` whose pattern field was empty, pointing at a line that contains no `claude` text at all. The cause is line-ending handling: the working-tree `.gitignore` is CRLF, because the repository sets `core.autocrlf=true`, while the committed blob is LF-only. A CR-only blank line is not an empty line to git's ignore parser — it is a pattern that matches EVERY directory, and `check-ignore` reports it with an empty pattern field, which is why the output looked like a tab-indented `.claude/` rule. The anomaly is confined to `check-ignore`'s REPORTING: `git status`, `git ls-files` and `git add` are all unaffected by it, and a receipt written under `.claude/` is still reported by `git status --porcelain -uall`. This was confirmed in a clean scratch repository with no `info/exclude`, with the real bytes and with an LF-normalised copy, and by comparing `git status --porcelain -uall` output between the two. The committed `.gitignore` is LF-only and carries no such line, so the artifact exists only in the working tree.

Because the guard derives its prune set from git rather than from a hand-maintained name list, the artifact was investigated against the guard's actual behaviour rather than merely explained. Git collapses an ignored directory to a single entry only while everything beneath it stays invisible: as soon as a git-visible file appears under it, git reports the specific entries instead of the collapsed one, and the directory is scanned again. A receipt planted under `.claude/` is therefore both visible to `git status` and found by the guard. This was verified across nine locations — the repository root, `.claude/`, `.wrangler/`, `a2a-stack/`, a nested `tmp/`, a nested `node_modules/`, `docs/`, `skills/`, and the repository-root `tmp/` — by planting a receipt carrying the lane's own token in each and comparing the guard's visibility against `git status --porcelain -uall`. The two agree exactly: nothing git can see is missed by the guard, and the guard reports nothing git cannot see.

## Goal supervision can be lost silently

Status: repaired, pending independent nonauthor acceptance; priority: P1. Found and reproduced on 2026-11-04 by the supervisor, in `a2a-stack/autonomy/manager.py`.

`GoalManager._launch` created the per-goal watcher task with `asyncio.create_task` and attached no done-callback, and nothing in the stack ever called `.exception()` on a watcher; the only retrieval was `close()` at host shutdown. `_watch` caught exceptions only around the controller spawn/wait block, and its recovery loop around the RECOVERING state publish re-raised any `PermissionError` whose winerror was not in `(5, 32, 33)`. An exception escaping `_watch` therefore ended supervision with no trace.

The consequence was not cosmetic. When the RECOVERING publish failed with a non-recoverable error (`OSError` errno 28, or `PermissionError` winerror 87), the watcher died silently: `host-events.jsonl` recorded only `controller_started` and `controller_exited` with no event for the loss, `state.json` still said `status=RUNNING`, and `report()` returned `status=RUNNING` with `next_user_action="Agent 正在自主执行，无需手动救场。"` — telling the owner the agent was autonomously executing while nothing was supervising the goal and nothing could relaunch its controller. This contradicts the standing acceptance criterion that a goal must not report autonomous progress it does not have, and the rule that a live process is not proof of progress. The user-facing path is the MCP `get_goal_report` tool, which returns exactly this report.

Advisor Council consulted (gemini-3.8-flash-advisor, request_id chatcmpl-agy-968d833a57a5) and advised combining a durable done-callback event with a live derivation of supervision state, so the report cannot claim autonomous execution even when the durable state write also fails. That advice was checked against the source rather than accepted on its authority, and the advisor's own stated risk was real: a done-callback also fires on normal completion and on cancellation, so without discrimination it would report a false supervision loss on every shutdown and every explicit cancel.

The repair therefore discriminates every non-loss case: manager closing, watcher cancelled, watcher exited without an exception, a `cancel.request` present, and a goal already terminal. A goal that reached `COMPLETE` is explicitly not downgraded, because a watcher dying after the goal finished supervised nothing that still needed supervising; an earlier draft of this repair used the broader `TERMINAL` set and would have overwritten an accepted result with a false blocker, which the supervisor caught while reviewing its own change. `resume()` clears the loss flags so an explicit resume re-establishes supervision instead of leaving the goal permanently reported as unsupervised.

`a2a-stack/autonomy/test_supervision_loss.py` adds fourteen tests. All eight original tests fail against the pre-fix manager (two failures and six errors, every one of them the absence of the supervision-loss behavior) and pass against the repaired one. Full-suite verification in the real tree with the real project venv: runtime 28 OK, autonomy 112 OK, agent 113 OK; no existing test was modified, deleted, skipped or loosened. The increment is uncommitted pending independent nonauthor QA. Evidence is in `D:/northstar-artifacts/a2a-stack/watcher-supervision-loss/`.

An independent nonauthor review of this increment returned NOT READY. It had no shell, so its execution claims were unverified by construction, but it also raised four substantive findings by reading, and all four were checked against the source and confirmed, then fixed rather than argued away. First, the user-facing copy was wrong: a supervision-lost goal was reported `NEEDS_USER` with `blocker: null` and an action telling the owner to resolve "the verified external dependency in the report", which does not exist in this scenario, so the report sent the owner after a blocker that was never there. The loss now records its own blocker and its own action text, and the report surfaces `supervision_lost_reason` so the owner can see whether the cause is transient (a disk-full `OSError`) or persistent (a permission fault that `resume` will re-crash into). The ordinary `NEEDS_USER` copy is unchanged, and a test pins that the supervision-loss copy does not leak onto ordinary blockers. Second, a loss belonging to a watcher that had already been superseded could clobber a resume: the done-callback ran after `resume()` had installed a fresh watcher, so the goal the owner had just resumed was reported unsupervised again with no hint that the resume was undone. The loss handler now only applies to the watcher that currently owns the goal. Third, a `COMPLETE` goal could be downgraded to `NEEDS_USER` by a watcher that died after it completed, because the persisted loss flag was checked before the terminal status. The terminal check now comes first for `COMPLETE` and `CANCELED` only; `NEEDS_USER` is itself in the terminal set and must keep reporting its loss, so the ordering is deliberate rather than a blanket reorder. Fourth, one original test did not exercise what its name claimed: it completed the goal BEFORE launching the watcher, so the watcher returned normally and the publish failure was never reached. It is retained as a guard and a genuine test was added that completes the goal AFTER the watcher has started, so the publish failure happens against a completed goal.

Scope limit: this makes the loss of supervision observable and truthful. It does not restart a dead supervisor, and it does not change the `NEEDS_USER` meaning elsewhere in the stack, which denotes a verified external dependency. `NEEDS_USER` is defensible here on independent grounds: it is the only terminal status that both blocks new productive work through `goal_active()` and is recoverable through `resume()`.

### Sibling background tasks can also die silently

Status: repaired; priority: P2. Same defect class as the supervision loss above: a background task created with `asyncio.create_task` whose exception is never observed by anything.

`autonomy/manager.py` `_launch_cancel` creates `_finish_cancel` with no done-callback, and nothing ever calls `.exception()` on it. Reproduced on 2026-11-04: when the CANCELING/CANCELED state publish fails (OSError errno 28) while owned tasks remain unresolved, the task dies with that exception, `host-events.jsonl` records nothing, `state.json` stays `status=CANCELING` with its unresolved task ids, and the report says `正在清理本 Goal 的任务，系统会自动继续清理。` ("the system will automatically continue cleaning up"). The goal is then stuck in CANCELING forever, and `resume()` refuses that state ("Owned task cancellation is still recovering; resume after it finishes"), so it is not directly recoverable either. The deception is more direct here than in the supervisor-watcher case: the report promises an automatic continuation that has already stopped.

`agent/task_store.py` `RecoveringDatabaseTaskStore._monitor_task` had the same shape: `asyncio.create_task(self._monitor_processes(context))` with no done-callback. That task is the startup recovery monitor that marks an in-flight task `TASK_STATE_FAILED` once its native worker is no longer identity-matched. If it dies, a task whose worker exited would never be marked failed and would never get its `terminal.json` recovery receipt, so the host would report productive work as still in flight.

This arm was reproduced on 2026-11-04 and the consequences turned out to be wider than the inspection-based reading suggested. The monitor loop iterates over every watched task with no error isolation, so a single failing receipt write ended the whole loop and stranded every OTHER watched task as well. Measured against unmodified production: with two watched tasks and one injected `OSError` errno 28 on a receipt write, the monitor died with that exception, nothing in the stack observed it, one task was left `TASK_STATE_WORKING` with no receipt (so the host reported dead work as still in flight), and the other was left `TASK_STATE_FAILED` with NO receipt either, because the receipt write happens after the state commit and the loop died before it. `agent/task_store.py` has no logging or event journal at all, so the death left no trace. A host restart healed the still-WORKING task by re-running the recovery pass, but the FAILED task kept no receipt permanently, because the recovery pass only writes receipts for tasks it finds in an active state.

The repair isolates the failure per task, keeps the state commit and the receipt write separately retryable, and records the failure durably at `control/task-store-monitor-failures.json` so the loss is not silent. A receipt is still published only after the FAILED state is committed, so a receipt is never visible for a task the database still calls active; that ordering is preserved rather than relaxed. Advisor Council consulted (gemini-3.8-flash-advisor, request_id chatcmpl-agy-e0132c731e41) and recommended per-task error isolation plus a done-callback backstop over a done-callback alone, because a done-callback fires only after the loop has already ended and cannot keep the surviving tasks reported. `a2a-stack/agent/test_monitor_resilience.py` adds five tests; all five fail against the pre-fix store (four failures and one error) and all five pass against the repaired one. Full-suite verification in the real tree with the real project venv: agent 113 OK, autonomy 112 OK, runtime 28 OK; no existing test was modified, deleted, skipped or loosened. The increment is uncommitted pending independent nonauthor QA, and that QA has since run and returned NOT READY with five further findings of its own, described below. Evidence is in `D:/northstar-artifacts/a2a-stack/sibling-background-tasks/`.

The cancel watcher is now repaired as part of the F1-F5 fix round described below: it has a done-callback that records `host_cancel_lost`, the owned-task scan tolerates an unreadable stack file, and `resume()` permits resuming out of CANCELING when the cleanup is known to have died. Evidence is in `D:/northstar-artifacts/a2a-stack/sibling-background-tasks/`.

### The terminal receipt: a withdrawal that destroyed the authoritative record, and the monotonic repair

Status: repaired and independently accepted; priority: P1. Found on 2026-11-04 by an independent nonauthor review of the receipt-contract increment, and confirmed by the supervisor against the source and by executed probes.

One file per task, `terminal.json`, is the artifact the delivery owner reads to learn a task's outcome. Two writers publish it: the task store (on a terminal database commit, and on its recovery and monitor passes) and the job executor's `finally`-hook in `agent/service.py`. The receipt-contract increment made the store's publication authoritative: the receipt's `state` mirrors the authoritative database terminal state, the `recovery` evidence is kept only while the database agrees the task is FAILED, and the executor's write is provisional and never overwrites a state the store published.

To close the remaining gap — a receipt left over from an earlier life of a task id — the repair added a withdrawal: on any ACTIVE save the store unlinked the receipt and popped its pending-receipt entry. An independent nonauthor reviewer disproved that repair with executed probes. Its `probe_withdraw_gap.py` reported, against the real store: "the authoritative terminal receipt was DELETED by a later in-flight save: True"; the recovery evidence destroyed by the same save; and "the host's outstanding FAILED+recovery claim was silently dropped: True". Its `probe_withdraw_window.py` showed the withdrawal firing inside the window between the executor's provisional write and the terminal commit, so the receipt was absent exactly when it was supposed to be available.

The reviewer was right, and the reason is structural rather than incidental. The SDK's legacy task store (`a2a.server.tasks.database_task_store.DatabaseTaskStore`, reached through `LegacyTaskStoreAdapter`) is last-writer-wins with NO terminal-state guard; the supervisor measured that committing `TASK_STATE_COMPLETED` and then `TASK_STATE_WORKING` for one task id leaves the row at `TASK_STATE_WORKING`. So the database itself can regress a task from terminal to active, and a withdrawal keyed on "the incoming save is active" cannot tell a stale in-flight event from a genuine one. The withdrawal therefore destroyed the authoritative receipt, the interruption evidence, and the host's outstanding claim, all at once.

Advisor Council consulted (gemini-3.8-flash-advisor, request_id chatcmpl-agy-f8f16de39b4c) on the design fork: keep one file, or split `terminal.json` in two. Verdict: keep a single `terminal.json` and make the persistence monotonic — reject an active save for a task the database already holds in a terminal state — and remove the generic active-save unlinking; its stated risk, that rejecting in-flight updates may raise unhandled exceptions in upstream SDK code unless handled as an idempotent no-op, is why the refusal is a silent no-op rather than an exception. A prior route (`gemini-3.1-pro-advisor`) was unavailable: the bridge returned HTTP 502 "model Gemini 3.1 Pro (Low) is not recognized as a known model". No fallback was substituted.

The repair has three parts. First, the store's `save()` is monotonic: it re-reads the task under the write lock and, when the database already holds a terminal state, refuses an incoming non-terminal commit instead of moving the row back into flight. A terminal commit may still supersede another terminal commit; the last terminal writer wins and the receipt is republished to match it. Second, the withdrawal is gone from the generic save path and survives only where the host has verified the native worker is ALIVE and has re-committed the task as genuinely in flight — the startup recovery pass and the unrecovered-task retry. Both of those now re-read the task under the write lock before committing, which the recovery pass's alive branch did not do before: it committed WORKING from the list snapshot it took at the start of the pass, so a task that had finished since the snapshot was moved back into flight and had its receipt retired. Third, a retired receipt is now recorded at `control/task-store-retired-receipts.json` instead of being silently dropped, so the host's outstanding FAILED+recovery claim is never lost without a trace.
