# Technical debt

## A2A root scopes containing live operational state

Status: partially closed; priority: P2. Observed during the 2026-11-03 Instacart readiness work.

The default Northstar workspace contains its own `tmp/a2a-stack` state tree. A whole-workspace `.` scope therefore includes changing journals and live lock files; snapshotting can fail with `PermissionError`, and operational changes invalidate candidates. The corrected root matcher deliberately includes all authorized files and fails closed. It does not silently omit state or `.git`.

The current eight-file framework Goal and prepared nine-file Instacart Goal use explicit paths and avoid this overlap. Their acceptance does not establish stable self-hosted whole-root execution.

Closed on 2026-11-04: `GoalManager.create` now rejects a write scope that overlaps the operational state root, in both containment directions, before any baseline read and before any Goal is persisted. The refusal is a clear diagnostic, not a silent trim, so scope completeness is preserved. Verified by independent nonauthor review (READY) plus a supervisor live-service check over the real HTTP surface: an overlapping scope returns HTTP 400 with the diagnostic while a state file is held under a real exclusive Windows lock, and no goal directory or goal record is created; a safe scope still returns HTTP 201 with a baseline holding only the scoped source files.

Still open: there is no dedicated state-root setting. `SHARED_STATE_ROOT` is a hard-coded constant, so the only way to move the state tree outside the workspace is to select a workspace whose namespace already lives outside it. The diagnostic says so explicitly rather than promising a configuration that does not exist. An explicitly configured external state location, with a reviewed migration that preserves existing default-workspace data, remains the separate follow-up. Preserve completeness: do not quietly skip unreadable or changing scoped files. Verify with isolated lock/state fixtures before broadening the supported configuration.

## Windows checkpoint replacement contention

Status: open efficiency follow-up; priority: P2 while automatic recovery converges. On 2026-11-03 the actual Instacart Goal `g-2ab099f9f9424d93917be136905cf3da` recorded one `WinError 5` replacing `state.json`. The existing harness resumed the same session without interrupting its separate coding worker. The actual holder and cause remain unknown; this is not evidence of an external blocker.

Owned Windows 10.0.26200 / NTFS fixtures reproduced the error with a held ordinary reader. A reader allowing read/write/delete sharing still blocked `os.replace` of its open target, although renaming that open source to a new name succeeded. The proposed reader-only repair failed its effectiveness test and was reverted in the private copies; production was unchanged.

`ReplaceFileW` passed a limited open-target fixture with share-delete readers, but Microsoft documents partial-failure states (1176/1177) that can move or remove the destination. It was not adopted as an atomic writer. See [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) and [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew). The controlled fixtures establish a platform vulnerability, not attribution of the actual incident or crash/power-loss durability.

Reopen if contention repeatedly prevents progress or measured owner restarts warrant a dedicated fix. Preserve same-Goal recovery and atomic snapshots; do not silently weaken durability, overwrite in place, change file permissions, kill readers, or block the host event loop with an unbounded synchronous retry. A replacement must pass failure-state and concurrent-snapshot checks before deployment. Diagnostic evidence is retained privately under `tmp/a2a-stack/instacart-soak/state-reader-repair/`.

The later reviewed snapshot-recovery increment keeps the existing writer unchanged and avoids model diagnosis for recognized owned-state write errors only after recovery persistence succeeds. It also closes the post-spawn cleanup gap. These are separate from the unresolved Windows replacement API/holder investigation; neither establishes a new writer or attributes the original lock.

## Claude shared auto-memory writes outside isolated source scope

Status: closed for the default Claude child paths; priority: P2. Closed native tool-path metadata for the formal-review/Claude-wait repair records three writes under the shared Claude project-memory directory, outside its private source write scope. Prior bytes were not captured, so no deletion or rollback was attempted. Candidate source correctness and the final isolated Python test audit do not establish native worker scope compliance.

Closed on 2026-11-04: both Claude child spawn sites now pin `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, child-only, in the copied environment and in the inline `--settings` payload, alongside the existing background-wait flag. `agent/service.py` `_child_env(True)` and `autonomy/runner.py` `NativeBackend.process` for the owner and supervisor channels set it; a non-Claude check child keeps exactly the inherited environment, and the parent environment is never mutated. The two strict full-map settings assertions were expanded to `{"env": {BG_WAIT_FLAG: "0", AUTO_MEMORY_FLAG: "1"}}`; every original test method and unrelated assertion is retained, and new cases are additive.

The flag was verified against the installed CLI rather than assumed. A control run without it wrote a native auto-memory file into a throwaway project memory directory; the same prompt with the flag produced zero memory files. The installed Claude Code 2.1.251 binary contains the `CLAUDE_CODE_DISABLE_AUTO_MEMORY` gate. The real Northstar project memory store was not touched by that test and the control's global-config side effect was reverted.

Both delivery mechanisms were then verified independently, because they are redundant by design and either could have been the inert one. The CLI honors only the **last** `--settings` occurrence, so a flag added as a separate occurrence would have silently discarded the other; both production sites therefore already use a single combined payload, which was confirmed by experiment and is recorded in `D:/northstar-artifacts/a2a-stack/claude-cli-settings-semantics.json`. A three-arm run against the installed CLI showed a control arm writing two native memory files, a plain-environment arm writing zero, and an arm where the flag was delivered ONLY through the inline `--settings` payload (with the child environment variable removed) also writing zero. So the `--settings` route is effective on its own and neither mechanism depends on the other; evidence is in `D:/northstar-artifacts/a2a-stack/auto-memory-settings-route.json`. The throwaway project namespaces from that run were removed afterwards and the real Northstar memory store was left untouched.

Scope limit: this suppresses native automatic memory reads and writes for those child paths. It is not an OS sandbox for arbitrary tool access, and it does not address any other writer to the shared memory directory.

Independent nonauthor acceptance on 2026-11-04: **READY**, bound to the four-file working-tree bytes. The reviewer found no defect in scope, confirmed both delivery routes are independently effective, confirmed the single-combined-`--settings` shape honors the last-occurrence-wins invariant, and confirmed the two strict payload assertions were expanded rather than loosened with no skip added or removed. The reviewer's own session had no execution capability, so the three green suites (runtime 28 OK, autonomy 106 OK, agent 104 OK) and a 14/14 external probe are the supervisor's evidence of record rather than the reviewer's own reproduction; the reviewer bound to the candidate by re-reading every scoped region and confirmed the content was byte-identical to the hashed bytes it was given.

The same review raised two documentation-clarity suggestions, both of which the supervisor then applied as the reviewer's exact text. The comment now claims only what was measured (the write side, on CLI 2.1.251) and names the two residual unmeasured effects (memory reads, and the user-level `CLAUDE.md` write) instead of the broader earlier "reads and writes" phrasing. The combined payload constant was renamed from `BG_WAIT_SETTINGS` to `CHILD_SETTINGS`, because the old name understated a two-flag payload whose SINGLE-occurrence shape is load-bearing; the comment above it now states that invariant explicitly. The rename touched only the two production files, the two test files reference the flag strings as literals rather than the constant, and the agent and autonomy suites still pass (104 OK, 106 OK) with no test churn. The external probe was updated for the new constant name so the artifact does not silently break; it remains 14/14.

For the optional Harness2 comparison, both execution arms must disable auto memory identically in their child environment and invocation settings before real model execution; preserve model, authentication, parent environment and project instructions. The official [Claude Code memory documentation](https://code.claude.com/docs/en/memory) documents `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Validate the installed CLI behavior and child-only configuration; a prompt write-scope alone is not an enforcement boundary. Production-wide isolation changes require a separate reviewed increment and are not part of the current five-file repair.

### Third Claude spawn site is not covered by the pin

Status: open; priority: P2. `a2a-stack/runtime/runner.py` is a third place in the stack that spawns a Claude child. Its `broker()` copies the parent environment with a plain `os.environ.copy()` and its `claude_command()` passes no `--settings` at all, so neither the auto-memory flag nor the pre-existing `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` background-wait flag is set on that path. This was found by an independent nonauthor review of the auto-memory increment, which found no defect in the reviewed change but flagged this coverage gap.

The path appears to be a diagnostic/legacy CLI route: the autonomy layer imports `runtime/runner.py` only for `atomic_json`, `Job`, `now` and `process_token` and never calls `runtime.broker`, and no documentation, scheduled task or production caller invoking the runtime broker's Claude mode was found. That lowers the risk but does not remove it, because this is the path most likely to reproduce the original incident if it is ever used. The repair is prepared and validated in a private tree (four new tests: 4/4 pass against the patched broker, and against the unpatched broker one fails and two error because the constant is absent) but is not yet applied to production, because `runtime/runner.py` is under separate independent review for the checkpoint-writer increment and editing it now would invalidate that review's candidate identity. Apply it as its own reviewed increment.
