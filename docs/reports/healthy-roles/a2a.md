# A2A practice and role-boundary analysis

Status: complete. Date: 2026-09-29. Scope: independent source/contradiction analysis for [Healthy functional roles and independent acceptance](../../goal/healthy-roles/GOAL.md). This report proposes Markdown practices and scenarios; it does not implement protocol support or evaluate another worker's changes.

## Current contradictions to resolve

- [Codex QA](../../../skills/codex-qa/SKILL.md#challenge-the-result-then-repair) says at line 33: “Without independence, make a separate review pass and disclose it.” That gives the builder a route to supply purported QA when no independent reviewer exists, directly conflicting with the goal's categorical ban on a builder independently testing, QA-reviewing, or judging taste/experience on its own deliverable. A disclosed self-check is still useful as a builder check, but cannot satisfy independent acceptance; absent independence, report the gap and leave acceptance to an eligible independent role or owner.
- [Northstar](../../../skills/northstar/SKILL.md#match-process-to-the-work) line 58 says “One agent filling several roles makes one acceptance decision”; [GOAL template](../../../skills/northstar/templates/GOAL.md#acceptance) line 45 says one agent filling all roles records one acceptance decision. These do not explicitly override the stricter goal rule, but permit builder/acceptor collapse unless the role conflict is named. Preserve one decision record while explicitly disallowing a builder from independently accepting their own artifact. Compatible functions can still combine on one agent where no conflict exists.
- The role table in [Northstar](../../../skills/northstar/SKILL.md#ownership-north-star--goals--tasks) lines 129–131 and [Codex Subagents](../../../skills/codex-subagents/SKILL.md#roles-and-authority) lines 47–49 defines orchestrator/supervisor/worker and critic/verifier assignments, but does not distinguish substantive functional roles from hierarchy. This can leave a task staffed with a manager and builder without the product, architecture, research, operations, or domain function needed to resolve its actual uncertainty.
- [Supervisor template](../../../skills/codex-subagents/templates/supervisor.md) says “Own integration and task acceptance” and [orchestrator template](../../../skills/codex-subagents/templates/orchestrator.md) says “Own integrated delivery” and inspect goal coverage; neither template asks whether the acceptor authored/changed the deliverable. A manager taking over worker repairs would also become its builder; its own repair checks cannot replace a fresh independent review.

Practical rule suggested for integration: treat *who builds, who checks, and who accepts* as separate accountability assignments when acceptance independence is required. An agent may wear multiple functional hats (for example, product analyst + domain researcher, or architect + implementer) if they do not create a self-review conflict. An independent reviewer can inspect after a combined builder finishes. If no eligible reviewer exists, mark the criterion unverified/pending owner acceptance; do not relabel the same agent or promote its own tests into acceptance. Manager repairs inherit builder status for the repaired portions and require independent reinspection.

## Verified A2A principles and Northstar adaptation

Primary sources checked 2026-09-29:

- [A2A Specification: Agent Card purpose and discovery](https://a2a-protocol.org/latest/specification/#81-purpose) says the card describes identity, capabilities, skills, and interaction requirements; clients use it to discover suitable agents and configure interactions. Its capability-validation section says clients should inspect declared capabilities before attempting optional operations. This is capability/fit discovery. The specification separately defines authentication and authorization, and explicitly says an `AUTH_REQUIRED` transition alone does not authorize an operation. **Northstar adaptation:** capability or role-profile match is routing metadata, never permission or user authorization; carry the actual authorized scope and limits in each assignment and check them before side effects.
- [A2A core data model](https://a2a-protocol.org/latest/specification/#41-core-objects) gives a task an `id`, optional `contextId`, status, artifacts, and history; messages have message IDs and may reference task/context; artifacts have IDs unique within a task. [Life of a Task](https://a2a-protocol.org/latest/topics/life-of-a-task/) describes context continuity, task refinements, and terminal task immutability. **Northstar adaptation:** retain the existing goal/task/report paths as durable identity; identify the exact deliverable/revision and link evidence; keep the same task identity across clarification/recovery, creating a linked follow-up only when the scope/outcome is genuinely new. These are useful analogies, not adopted fields or wire objects.
- [Task states](https://a2a-protocol.org/latest/specification/#413-taskstate) distinguish `COMPLETED` (successful task), `FAILED`, `CANCELED`, `REJECTED` (terminal), and `INPUT_REQUIRED`/`AUTH_REQUIRED` (interrupted). [Multi-turn interactions](https://a2a-protocol.org/latest/specification/#34-multi-turn-interactions) continue with the same task/context identifiers when input is needed. **Northstar adaptation:** state explicitly whether a handoff is working, completed, blocked/failed, canceled, or waiting on a named input/authority; silence, agent inactivity, or a context reset is not completion and must not erase attempts, evidence, acceptance criteria, or authorization. Resume from the existing checkpoint.
- A2A task completion is a task lifecycle outcome, not the receiver's acceptance decision. **Northstar adaptation:** treat `completed` as “worker says its assigned task/output is complete”; supervisor/orchestrator acceptance is a distinct documented judgment against criteria, and required human acceptance remains separate. This distinction is our practice, not a claim that A2A protocol semantics prescribe Northstar review roles.
- A2A supports a lightweight direct `Message` for stateless/simple exchange and a tracked `Task` for substantial work requiring status/artifacts; it does not require every communication to become a workflow. **Northstar adaptation:** concise direct peer clarification for a small interface question; durable task/report/checkpoint for delegated work with multiple steps, material dependencies, evidence, or recovery history.

The recommendations above borrow concepts, not A2A semantics as a contract: Northstar remains a Markdown practice package. Do not claim A2A interoperability, wire compatibility, a schema, runtime task state, or enforcement. Official references describe an actual protocol with protocol objects and implementation rules; our profiles, reports, authority checks, completion, and human acceptance are human-readable instructions and records.

## Adversarial scenarios to exercise (proposals, not executed)

1. **Builder labels self as QA after implementation.** Expected: its functional/unit checks remain builder evidence; it cannot produce independent acceptance or taste judgment. Assign a different agent who did not author the artifact, or leave independent review/acceptance pending and disclose the gap.
2. **One agent combines compatible roles, then reviews its own changes.** Example: product analyst + domain researcher + builder. Expected: combining compatible analysis functions is allowed, but it remains the builder for affected output; a distinct reviewer checks against original user criteria. Role renaming does not restore independence.
3. **Supervisor fixes integration defect in worker artifact and declares ready.** Expected: supervisor becomes author of the repaired slice, performs useful development checks, and obtains independent review of that slice and affected integration before acceptance; no manager self-certification.
4. **Capability profile says “can deploy,” assignment only authorizes local code edits.** Expected: do not deploy. Profile/capability discovery cannot enlarge task authority, user authorization, or tool permissions; report exact missing authorization if deployment is necessary.
5. **Reviewer cannot access rendered UI/reference or test environment.** Expected: name the unavailable evidence and impact, set result to unverified/not ready as appropriate, request a safe access path or eligible owner decision; do not substitute builder screenshots or checklist self-attestation for visual independence.
6. **Agent context resets or goes silent after `working`; later a new agent is assigned same criterion.** Expected: restore task identity, criteria, authority, changed artifact, actual evidence, failed attempts and recovery window from checkpoint; silence/reset is not completion, and reassignment does not reset recovery. If input is needed, state exactly what and who owns it.

These cases test the goal's proposed boundaries and handoff semantics; they have not been run against the new profiles or package.
