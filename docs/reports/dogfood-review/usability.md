# Usability and economics review

**Review basis:** current working tree, as scoped in `docs/goal/dogfood-review/GOAL.md` (base `265c9db` plus preserved package and operating-system changes). This is a document walkthrough, not a user study or executed task outcome. I read the entry README and install guide, the Northstar and Subagents skills, the direction and record indexes, and the operating-system ceremony rules. I did not inspect other dogfood reports before forming this judgment.

## Judgment

Northstar has the right low-cost defaults, but its first-use story is much shorter than its operating manual. The entry path explains which skill to invoke and explicitly says four installed skills do not mean four agents; the deeper skills contain strong controls against unnecessary delegation, retries, and ceremonies. The main usability risk is that the mandatory learning/review language is prominent, while the compact routine-task exception is buried. The main economics gap is evidence: the package knows what to count, but current local evidence does not establish lower total cost per accepted outcome.

The highest-value next move is a small, matched task-use pilot that tests whether the current package changes accepted outcome and total effort. Make one compact “routine task / more involved task” route easier to see while running that pilot. Defer another process expansion until the pilot shows a concrete failure or useful capability gap.

## Newcomer path and skill burden

The README is a reasonable front door: it defines Northstar, names the four skills, links one installation flow, and tells the user to start with `$northstar` plus an outcome. The install guide gives a copy-all-four PowerShell example and explains that advisor service setup is separate. It also explicitly says companions are loaded only when needed. This is a clean mental model, though someone who only wants a first task must read through upgrade and optional advisor details to reach the later “continue existing work” prompt.

As a rough size signal, not a token estimate, the current README has 36 lines and about 434 whitespace-separated words; the install guide has 56 lines and about 521. The central skill is 173 lines / about 4,213 whitespace-separated words, and Subagents is 107 lines / about 2,158. The front-door docs are modest; the cost is in the amount of guidance a reader or agent may feel obliged to load. The core skill has useful headings and repeatedly says to load only relevant companions/references, so the full word count is not the same as the per-task context burden.

**Document walkthrough: simple task.** A newcomer installs the sibling bundle, invokes `$northstar` with a concrete outcome, resumes any applicable current state, and implements the smallest complete workflow. For a one-turn task, the user request/handoff can define the delivery; a small local change needs relevant checks and a short result. If it changes a user workflow or visible artifact, the skill routes to a brief QA pass. On acceptance, the agent reports the result, checks, and limits, then closes learning in the existing record; it does not create a project lifecycle or a report file just because Northstar is installed. This path is coherent, but the “small local change” allowance and one-entry learning treatment sit in the skill body rather than the README’s first-use path.

**Document walkthrough: stalled/team task.** When a criterion stalls, the core skill names a distinguishing check and a default reassessment boundary of five investigative calls or ten minutes; preserves the last verified state; counts attempts across agents and context switches; then requires a bounded recovery and an executable disposition. The team path first defaults to one agent and only delegates independent, reviewable work likely to repay coordination/integration cost. If delegation is justified, the brief carries outcome, acceptance, authority, interfaces, and handoff. The accepting manager inspects the integrated result. A decision meeting is triggered by material disagreement that remains after one direct evidence exchange (or an immediate authority/acceptance threat); preference alone cannot block acceptance. These rules are unusually explicit and economically sound on paper. This walkthrough does not show that a real agent or user followed them or that they reduce elapsed time, tokens, or rework.

## Process clarity and ceremony burden

The trigger logic is better than a generic “always use the framework” package: ordinary decisions stay local; team structure scales with dependencies; QA is tied to changed workflows/visible artifacts or material risk; advisor consultation requires a material knowledge gap; the disagreement meeting is triggered by unresolved material disagreement; and unchanged polls are not checkpoints. `Northstar` also says a small local change needs only implementation, relevant checks, and a short result. These details should be the first thing a new user sees.

There is still a presentation risk. “Self-learning is part of delivery” appears prominently in the README and the first section of the skill, and the core skill calls the checkpoint review mandatory. The compact routine case—request/handoff can suffice, no report file for single-agent changes unless required, and a few lines for routine work—is distributed later. A skimming reader could infer that every small task entails a retrieval and documentation ceremony, even though the actual text scales it down. The Subagents skill also repeats checkpoint/acceptance obligations from Northstar in its six-step coordination section and the role briefs. The duplication is defensible for direct invocation, but the combined impression can be heavier than the behavior requires.

Recommendation: keep the substance; add a very short top-level routing box or worked prompt showing (a) routine one-agent task, with relevant checks and a compact closeout, and (b) the conditions that load QA, Subagents, or Advisor. At the same time, choose one canonical explanation for checkpoint-learning requirements and make companion skill/brief repetitions point back to it while retaining role-specific actions. Do not turn the box into a new checklist or make folder/report creation a prerequisite.

## Economics and measurement

The allocation rules are strong: prefer a capable lower-cost worker for bounded work, reserve stronger reasoning for direction/integration/consequential decisions, and include manager, consultation, review, retries, and rework in comparisons. They explicitly require matched tasks with unchanged acceptance and comparable starting states; unavailable token/cost data must remain unknown. That is the right measurement contract.

What remains unknown is practical: no token, provider cost, elapsed-time, or total-effort results are attached to an actual accepted-task comparison here. The goal itself distinguishes prior package/recovery trials from proof of held-out improvement or savings. A synthetic handoff or a reduced expert-call count can support feasibility, not savings. The report does not have access to measured runtime usage for this document review, so all model/provider cost is unknown; no token claim is inferred from document word counts.

Next, run a small matched pilot across routine work, a multi-part task where delegation could help, and a task with a real failure or integration issue. Compare the existing Northstar route with the current direct/previous route while preserving task acceptance and similar starting conditions. Capture whether each task was accepted, elapsed time, attempts and interventions, coordination/review/rework, model and role, and actual usage/cost wherever the runtime exposes it. Count takeover as rescue, not worker success. Report missing usage as unknown and stop the efficiency claim if comparable data cannot be gathered. Use results to decide whether the quick-start needs revision and where capability allocation actually saves or costs effort.

## Priorities and scope

1. **Measure outcome and all-in effort on matched tasks.** This resolves the largest product uncertainty and constrains further process additions. Include simple, delegated, and failure/recovery examples; keep acceptance stable and disclose unknown usage.
2. **Make the low-ceremony route visible.** Show the simplest first action and what makes QA, Subagents, Advisor, or an operating ceremony apply. Preserve the current granular pages as reference material.
3. **Consolidate repeated checkpoint wording after the pilot.** Reduce duplicated obligation language where it adds no local instruction. Do not trim failure history, authority boundaries, evidence quality, or actual handoff responsibilities based on length alone.

**Keep:** the one-agent default, evidence-backed acceptance, bounded stall recovery, full-cost accounting, authority boundaries, and direct unresolved-disagreement route.

**Remove/merge:** repeated generic checkpoint/learning explanations across core, Subagents, and role briefs; retain concise role-specific duties and links to the canonical rule. Remove no acceptance gate based solely on page length.

**Defer:** more agent-capacity guidance, additional ceremony types, stronger-model defaults, or claims of “cheaper” execution until real comparable task evidence identifies a need. Also defer broad competitive positioning: the direction document itself says demand and comparative performance remain unvalidated.

## Proposed North Star and counterargument

**Proposed North Star:** Help an owner get an accepted outcome with the least total supervision and effort: keep routine work direct, and add coordination, review, or stronger capability only when evidence shows it changes acceptance, risk, or the next decision. Count the whole path, including retries and repair.

The strongest counterargument is that a short visible path may overcorrect toward speed and hide the quality, authority, and handoff protections that address known agent failure modes. Skipping them can make the first task look cheaper while producing an unintegrated or unsafe result and shifting cost to the owner. The response should be to make escalation conditions visible, not to remove necessary checks: keep risk-sensitive acceptance firm, and let a matched pilot decide whether the quick-start language causes omissions.

## Checkpoint self-review

- **What worked:** reading the entry docs alongside the operative skills exposed a tension between strong modularity and a less-visible routine-task exception; the exact trigger rules resolve several apparent ceremony concerns.
- **What failed or remains unknown:** there is no newcomer observation, real task-use comparison, or usage/cost receipt in this review. The document walkthrough cannot establish behavior or savings.
- **Decision and next check:** test the proposed first-use routing and all-in measurement in matched tasks before expanding Northstar. Reopen the wording recommendation if the pilot shows that users already find and apply the routine path reliably, or if it contributes to missed quality criteria.

## Peer exchange

**Routine-task routing before the pilot vs. freezing first.** The product report proposes using the initial matched pilot to decide whether invocation needs simplification; QA likewise recommends a bounded later evaluation. I agree with that order and revise my earlier preference to make routine routing more visible before the first comparison. A wording change immediately before the pilot could blur whether an observed effect came from Northstar's current operating guidance or the changed entry path, especially if the comparison is meant to characterize the current package. Freeze and identify the package revision for the first cohort, record any discoverability failure as an outcome, then make a separately identified routing revision and compare it in follow-up if users actually miss the right path. This preserves mandatory checkpoint reviews; the pilot must not test a weaker process by removing them. My remaining disagreement is only sequencing emphasis: the compact route is still a likely improvement, but its timing should depend on the frozen-cohort evidence. If users cannot identify the first action or companion when needed, that is the evidence that changes my view and justifies a targeted revision.

**Software cohort first; business operations as a separate next cohort.** I agree with product's proposal to start with bounded software work, because acceptance and integration can be judged against concrete workflow criteria, and with QA's requirement to keep outcome and cost claims bounded to the actual cohort. This is sequencing, not narrowing Northstar's intended project/business scope. Keep business-operations validation as an explicit later cohort with its own observable operating outcomes and review period; software results alone cannot establish the broader promise. Reopen the sequence if suitable software tasks are unavailable or the next material decision concerns an ongoing business operation. I do not see a material remaining disagreement with either peer on this point.
