# Spot Advisor 2.1 critical review

The product bet is that a developer can leave Spot Advisor enabled on routine work and get more tasks finished without paying for frontier execution throughout or stepping in more often. The frozen public comparison recorded 23 of 29 eventual passes for Luna with optional advice and 22 of 29 for Astra alone. It compared complete workflows and had incomplete usage coverage. The next decision is whether a consultation earns its place in a developer's existing workflow.

## Ten challenges and the decision on each

| # | Challenge | Decision and rationale |
| --- | --- | --- |
| 1 | Would Luna have solved it with one more attempt? | **Address.** Extra effort could explain a recovery attributed to advice. Compare both continuations from the same failed state. Without this result, the research claim and the product case remain uncertain. |
| 2 | Why install a skill when the developer can switch to Astra at the point of failure? | **Address.** An immediate handoff is a distinct alternative to both Luna continuing and Astra starting from scratch. If it finishes more work with similar cost and effort, the skill has a weak reason to exist for that task class. |
| 3 | Can the advisor recover when the executor sends the wrong diagnosis or too little evidence? | **Address.** Short packets are central to the product's economics and constrain what the advisor can infer. Advice that sounds plausible can send an otherwise recoverable task in the wrong direction. |
| 4 | Do savings survive retries, failed tasks, missing receipts, and extra human effort? | **Address.** A lower frontier token count cannot establish commercial value on its own. A favorable average can also conceal costly failures in a task class where advice is enabled by default. |
| 5 | Can an ordinary developer install it, recover from a routine interruption, and choose to use it again? | **Address.** Benchmark results cannot show whether users adopt the normal workflow. Observe first use and repeat use on real work, including one interruption that tests whether the developer has to reconstruct context or intervene. |
| 6 | Should 2.1 guarantee recovery across every provider failure, crash boundary, and concurrent launch? | **Defer broad coverage.** Existing tests cover an interrupted dispatch and a timeout after dispatch without a repeat. Keep these checks and fix any defect that blocks the normal flow in #5. Expand recovery when repeated failures justify the work. |
| 7 | Should it support every coding host and provider before release? | **Defer.** Codex and Claude Code give the initial study two hosts. Add further integrations when the first users need them and their behavior can be checked end to end. |
| 8 | Should 2.1 include a deadline-based consultation policy? | **Defer.** The stated goal is completed, verified work in everyday use. Measure elapsed time to understand friction. Revisit a policy only for users who routinely work against a meaningful deadline. |
| 9 | Should it expose a dashboard for advice, usage, and routing? | **Defer.** Local receipts and a readable outcome are enough to investigate the five retained risks. Build a dedicated interface if repeat users have a decision that the existing records cannot support. |
| 10 | Should it predict the best trigger for every task class automatically? | **Defer.** The product needs evidence that advice helps at least one recurring kind of blockage. Start with an inspectable rule and use the results from #1 and #3 to decide whether broader automation is warranted. |

## Evidence required for the five retained challenges

1. **Incremental effect of advice.** Pick a recurring blockage and define eligibility before collecting results. Save the task, workspace and failed check before advice. Compare Luna continuing alone and Luna receiving one Astra reply, using the same executor settings, remaining budget and verifier. Keep failed deliveries and report paired wins and losses. If the advice arm has no meaningful improvement, narrow or drop the trigger.
2. **The direct-switch comparison.** Add an Astra takeover arm from the same saved blockage, with the same task evidence and resources to verify it. Count takeover effort and repeated investigation. Keep a separate Astra-from-start arm when measuring whole-workflow economics. If takeover produces better outcomes at similar total cost and human effort, recommend takeover for that class.
3. **Advice under imperfect context.** Include cases where the initial diagnosis was wrong, key evidence was missing, or a dependency had failed. Give the advisor a way to request one discriminating local check. Track unnecessary edits and cases where the no-advice continuation passed but advice failed. Tighten the default trigger or evidence requirements if a recurring class is harmed.
4. **Full-task economics.** For each arm report verified completion, input and output tokens by model, total model cost divided by verified completions, and manual takeovers. Include all attempts and failed tasks. Show usage coverage and check whether plausible costs for missing receipts would reverse the result. Report API-equivalent costs and observed subscription costs according to what the data supports.
5. **Repeatable use by developers.** Start with developers who already use a lower-cost coding agent and face the chosen blockage regularly. Observe whether they can install the skill, complete a real task, continue through a representative interruption, and voluntarily use it again. Record intervention counts and why anyone returns to direct model switching.

Run the matched continuations for #1 and #2 first, with the diagnostics from #3 and the accounting from #4 in place. In parallel, observe the smallest usable installation flow for #5. Use the results to decide which trigger and recovery work earns priority in the [2.1 roadmap](spot-advisor-2.1-roadmap.md).
